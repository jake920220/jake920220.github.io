## 들어가며: 똑똑한 대화 뒤에 남는 '지식의 휘발성'

최근 개발과 일상 전반에서 ChatGPT, Claude, Antigravity 같은 AI 도구들을 전방위로 활용하고 있다. 복잡한 아키텍처 설계나 기술적 의사결정, 새로운 라이브러리 검토부터 커리어와 교육 일정 관리까지 AI와 대화를 나누며 문제를 해결하는 일은 이제 자연스러운 일상이 되었다.

하지만 AI를 깊게 쓰면 쓸수록 한 가지 뼈아픈 한계에 부딪혔다.

AI와의 대화창 안에서는 놀라운 코드 스니펫, 치밀한 설계 아이디어, 유용한 인사이트가 쏟아져 나온다. 그러나 대화 세션이 종료되는 순간, 그 모든 지식과 컨텍스트는 파편화되어 사라진다. 다음 날 새로운 대화창을 켜면 AI는 어제의 나와 나눈 치열한 고민을 전혀 기억하지 못한다. 결국 "내가 저번에 어떤 결정을 내렸더라?", "그때 작성한 설정 코드가 어디 있었지?"라며 과거의 채팅 기록을 뒤적거리거나, 똑같은 배경 설명을 AI에게 처음부터 다시 타이핑하고 있는 나 자신을 발견하게 된다.

그렇다고 노션(Notion)이나 기본 메모 앱에 수동으로 기록하자니 또 다른 병목이 생겼다. 메모를 체계적으로 정리하려면 폴더를 고르고, 태그를 달고, 양식을 맞추고, 관련 문서를 찾아 링크를 걸어야 한다. 이 정리 노동(Friction) 자체가 피로해져 며칠 만에 '미분류 메모 덤프장'이 되어버리기 일쑤였다.

이 지점에서 개발자로서 한 가지 근본적인 질문을 던지게 되었다.

> 지식 관리는 왜 항상 인간이 일일이 손으로 분류하고 정리해야 할까?  
> 거대 RAG나 벡터 DB를 따로 만들지 않고도, 가장 단순한 로컬 마크다운 위에서 AI 에이전트가 직접 읽고 쓸 수 있는 상호작용형 지식 베이스(Agent-readable Context Store)를 만들 수는 없을까?

이 글은 그 고민에서 출발하여 옵시디언(Obsidian)을 기반으로 세컨드 브레인을 설계하고, AI 에이전트를 전담 사서(Librarian)로 연동하여 일상과 업무(강의 관리 및 정산)를 자동화한 실전 구축 기록이다.


## 대안 비교: 왜 별도의 벡터 DB 인프라가 아닌 로컬 텍스트+에이전트인가

처음에는 유튜브나 여러 개발 블로그를 통해 옵시디언 세컨드 브레인에 관한 이야기들을 많이 접했고, 로컬 마크다운으로 가볍게 시작하려 했다. 하지만 AI 도구들과 본격적으로 엮어보려다 보니 자연스럽게 한 가지 고민이 생겼다.

> "AI 기반 지식 관리라고 하면 다들 임베딩(Embedding) 모델을 서빙하고 벡터 데이터베이스(Vector DB)를 붙인 RAG 파이프라인을 만들던데, 나도 그런 별도의 백엔드 인프라를 먼저 구축해야 할까?"

물론 RAG(Retrieval-Augmented Generation)는 외부 지식을 언어 모델과 결합하는 훌륭한 방법론이며, 원본 문서를 보존하면서도 유연하게 인덱스를 둘 수 있다. 하지만 **개인 지식 관리(PKM)라는 도메인과 1인 개발자의 관리 비용** 관점에서 비교했을 때, 별도의 벡터 DB 인덱싱 시스템을 유지하는 것은 분명한 트레이드오프가 있었다.

| 비교 항목 | 별도 벡터 DB / 임베딩 파이프라인 구축 | 로컬 마크다운(Obsidian) + CLI 에이전트 |
| :--- | :--- | :--- |
| **인덱싱 방식** | 텍스트 청킹(Chunking) 및 임베딩 벡터 변환 | 순수 마크다운 파일 + 로컬 텍스트 색인 (`grep`, `find`) |
| **인프라 관리** | 임베딩 모델 서빙, 벡터 DB 서버, 동기화 파이프라인 필요 | 인프라 비용 0원, OS 파일 시스템과 Git으로 완결 |
| **수정 및 피드백** | 문서 수정 시 임베딩 재색인 파이프라인 동작 필요 | 파일 수정 즉시 에이전트가 최신 파일 상태 반영 |
| **도구 단순성** | 별도 검색 API 서버 및 파이프라인 연동 필요 | 에이전트의 기본 파일 읽기/쓰기 도구로 직접 상호작용 |

개인의 세컨드 브레인은 방대한 고정 문서를 읽기만 하는 아카이브가 아니라, **매일 문서가 추가·수정되고 할 일이 생겨나는 유기적인 작업 공간**이다. 별도의 인프라 서버를 띄우고 인덱싱 파이프라인을 유지보수하는 복잡도를 더하기보다, **가장 단순하고 투명한 로컬 파일 시스템** 위에서 코딩 에이전트(Antigravity 등)가 CLI 도구로 직접 읽고 쓰게 만드는 편이 1인 환경에 훨씬 기민하고 실용적이었다.


## 폴더 체계 설계: PARA와 Johnny.Decimal의 결합

지식 관리 방법론으로는 티아고 포르테(Tiago Forte)의 PARA 프레임워크(Projects, Areas, Resources, Archives)를 채택했다. 다만 이를 파일 시스템에 그대로 옮겼을 때 예기치 못한 문제가 발생했다.

일반적인 OS 파일 탐색기와 옵시디언 탐색기는 기본적으로 알파벳/가나다 순으로 정렬된다. 접두사 없이 폴더를 만들면 다음과 같은 역전 현상이 일어난다.

```text
📁 Obsidian Vault/ (알파벳 정렬 시의 문제)
├── 📁 Archives     # 거의 볼 일 없는 보관함이 최상단에 노출
├── 📁 Areas
├── 📁 Inbox        # 매일 열어봐야 하는 수집함이 중간에 묻힘
├── 📁 Projects     # 가장 활발히 실행 중인 프로젝트가 뒤로 밀림
└── 📁 Resources
```

이를 해결하기 위해 Johnny.Decimal 체계(숫자 접두사)를 결합했다.

```text
📁 Obsidian Vault/
├── 📁 00 Inbox/          # 정제되지 않은 날것의 메모, 임시 스크랩, 대화 덤프
├── 📁 10 Projects/       # 마감일과 명확한 결과물이 있는 진행 중인 작업
├── 📁 20 Areas/          # 지속적으로 관리하는 책임 영역 (Career, Frontend, AI 등)
├── 📁 30 Resources/      # 언제든 다시 참고할 주제별 지식 라이브러리
├── 📁 40 Archives/       # 완료되거나 비활성화된 보관함
├── 📁 90 Templates/      # 새 문서 생성을 위한 마크다운 템플릿
└── 📁 99 System/         # 볼트 운영 규칙, 자동화 스크립트, 에이전트 가이드
```

### 왜 10단위 숫자 프리픽스인가?

1. **지식의 생명주기 순서 고정**: `수집(00) → 실행(10) → 관리(20) → 참고(30) → 보관(40)`으로 이어지는 인지 흐름대로 시각적 정렬이 고정된다.
2. **유연한 확장성**: `10, 20, 30`처럼 10단위 간격을 두었기 때문에, 향후 주기적 회고를 위한 `15 Reviews`나 외부 협업 폴더가 필요해져도 기존 번호 체계를 깨뜨리지 않고 끼워 넣을 수 있다.
3. **분류 판단 기준의 단순화**:
   - 지금 명확한 결과물을 만드는 작업인가? → `10 Projects/`
   - 장기적으로 유지해야 하는 나의 역할/도메인인가? → `20 Areas/`
   - 나중에 다시 찾아볼 지식/학습 자료인가? → `30 Resources/`
   - 완료되었거나 보관할 자료인가? → `40 Archives/`
   - 당장 판단하기 모호한가? → `00 Inbox/`


## 외부 프로젝트와 볼트 연결: 심볼릭 링크(Symlink) 패턴

세컨드 브레인을 구축하며 마주친 현실적인 고민 중 하나는 외부 Git 프로젝트와의 데이터 동기화였다.

예를 들어, 지금 작성 중인 기술 블로그 포스트들은 Astro 기반 저장소(`~/blog/src/content/posts`)에서 Git으로 관리되고 있었다. 이 포스트들을 옵시디언 세컨드 브레인 안에서도 링크하고 지식 그래프로 연결하고 싶었다.

만약 블로그 글을 복사해서 옵시디언 볼트에 넣는다면, 한쪽에서 오타를 고쳤을 때 다른 쪽은 수정되지 않는 데이터 불일치(Single Source of Truth 위반)가 발생한다. 반대로 블로그 저장소 전체를 옵시디언 볼트 하위로 옮기는 것은 블로그 배포 파이프라인의 격리를 해친다.

이 문제를 해결한 도구는 운영체제의 원초적인 기술인 심볼릭 링크(Symbolic Link)였다.

```bash
ln -s "/Users/kimjunhyun/blog/src/content/posts" "/Users/kimjunhyun/Documents/Obsidian Vault/Junhyun_Second_Brain_Starter/30 Resources/Blog Posts"
```

```text
[ Astro Blog Repository ] ─── (Git 배포 파이프라인)
   ~/blog/src/content/posts/
              ▲
              │ (Symbolic Link)
              ▼
[ Obsidian Second Brain Vault ]
   30 Resources/Blog Posts/ ─── (양방향 링크, 지식 그래프 연결)
```

이 간단한 연결이 가져다준 효과는 강력했다.

- **Single Source of Truth**: 실제 파일은 블로그 Git 저장소에 단 하나만 존재한다.
- **무마찰 편집**: 옵시디언에서 블로그 글을 열어 수정하거나 백링크를 확인하면, 실제 블로그 소스코드가 실시간으로 수정된다.
- **지식 그래프 편입**: 블로그 글이 옵시디언 볼트 내부의 `[[React]]`, `[[AI 에이전트]]` 같은 다른 리소스 노트들과 `[[위키링크]]`로 자연스럽게 연결된다.

### 심볼릭 링크 도입 시 주의할 점과 링킹 원칙

심볼릭 링크는 편리하지만 실전 운영에서는 명확한 주의가 필요하다.

1. **Obsidian 공식 경고와 정기 백업**: 옵시디언 공식 문서에서는 심볼릭 링크 사용 시 파일 시스템 감시자 미동작, 동기화 충돌, 데이터 손실 위험을 경고한다. 따라서 볼트 전체와 블로그 저장소를 **Git으로 철저히 버전 관리하고 정기적으로 커밋**하는 안전장치가 필수적이다. 또한 볼트 내부와 링크 대상이 꼬이는 순환 참조(Circular link)를 만들지 않아야 한다.
2. **Astro 호환 링킹 원칙**: 현재 Astro 블로그는 옵시디언 전용 `[[위키링크]]` 파서를 기본 탑재하고 있지 않다. 따라서 블로그 글 원본(`.md`) 내부에서는 웹 배포 시 정상 작동하도록 **Astro 호환 표준 마크다운 링크(`[텍스트](경로)`)**만 작성한다. 반대로 옵시디언 볼트 내 다른 개인 노트에서 블로그 글을 가리킬 때만 `[[위키링크]]`를 사용하는 **단방향 링킹 규칙**을 세워 웹 렌더링 깨짐과 볼트 탐색을 모두 만족시켰다.


## AI 탐색 최적화: 검색 후 선별 독해 방식

로컬 AI 코딩 에이전트(Antigravity, Claude Code 등)에게 세컨드 브레인 볼트 관리를 맡길 때 가장 경계해야 할 것은 비용 낭비와 답변 품질 저하다.

만약 "내 옵시디언에서 프론트엔드 관련 내용 찾아줘"라는 요청을 받은 AI가 볼트에 있는 수백, 수천 개의 노트를 한꺼번에 전부 다 읽어 들이려고 한다면(Full Dump) 어떻게 될까?

이것은 마치 도서관 사서에게 질문 하나를 던졌을 때, 사서가 도서관 서가에 꽂힌 수천 권의 책을 통째로 복사해서 책상 위에 쏟아붓는 것과 같다. 엄청난 양의 글자를 읽느라 시간과 비용(토큰)이 낭비될 뿐만 아니라, 너무 많은 정보에 파묻힌 AI가 집중력을 잃고 엉뚱한 답변(환각)을 내놓기 십상이다.

이를 해결하기 위해 사람이 도서관에서 책을 찾듯 먼저 검색해서 찾고, 그 파일만 콕 집어 읽는 2단계 방식을 정립했다.

```text
[ 사용자 질문 / 요청 ]
        │
        ▼
[ 1단계: 검색 (색인 카드로 파일 찾기) ]
  ├── 파일명이나 디렉토리 구조 매칭 (find)
  └── 키워드가 포함된 문서 목록만 빠르게 색인 (grep)
  └── (AI에게 본문 전체를 읽히지 않으므로 비용 소모가 거의 없음)
        │
        ▼
[ 2단계: 선별 독해 (찾아낸 책만 펼치기) ]
  └── 1단계에서 좁혀진 딱 2~3개 관련 파일만 열어서 정밀 분석
  └── (수천 자 이내의 핵심 문맥만 읽으므로 가볍고 정확함)
```

이 2단계 방식을 적용하면 볼트에 노트가 수백, 수천 개로 늘어나더라도, **LLM 프롬프트에 불필요한 전체 덤프 없이 꼭 필요한 수천 자 이내의 컨텍스트만 선별 주입**하여 토큰 비용 낭비를 막고 모델의 집중력(환각 방지)을 효과적으로 유지할 수 있다.

### 지식 그래프 오염을 막는 3단계 링킹 규칙

또한 AI가 문서를 작성할 때 본문에 등장하는 모든 단어에 무차별적으로 `[[위키링크]]`를 걸어버리면, 지식 그래프는 의미 없는 스파게티 거미줄이 되어 가치를 잃는다.

이를 방지하기 위해 에이전트 운영 지침 문서(`AGENTS.md`)에 명확한 링킹 규칙을 명문화했다.

1. **단순 단어 일치 링킹 금지**: 본문에 우연히 '개발'이나 '공부'라는 단어가 나왔다고 해서 링크를 걸지 않는다.
2. **독립된 문서가 존재하는 상위 개념/프로젝트만 연결**: 실제 `30 Resources`나 `10 Projects`에 존재하는 구체적인 주제(`[[Claude Code]]`, `[[TypeScript]]`, `[[Astro]]`)만 링크한다.
3. **고립 노트(Orphan Note) 방지**: 새로 작성되는 문서는 반드시 최소 1개 이상의 상위 Area 또는 MOC(Map of Content, 목차 노트)와 연결되어야 한다.


## 시간축(Journal)과 주제축(PARA)의 하이브리드 결합

세컨드 브레인을 운영하다 보면 "매일 작성하는 일기(Daily Note)는 PARA의 어디에 두어야 하는가?"라는 구조적 난제에 부딪힌다. 일기는 1년에 365개씩 쌓이는 방대한 시계열 데이터다. 이를 일반 폴더에 무작정 쌓아두면 파일 목록이 오염된다.

이를 해결하기 위해 시계열 격리 폴더링과 양방향 링크 기반의 컨텍스트 집계 방식을 설계했다.

```text
📁 20 Areas/Journal/
└── 📁 2026/
    └── 📁 08/
        ├── 2026-08-20.md
        └── 2026-08-21.md
```

옵시디언 데일리 노트 플러그인의 날짜 포맷을 `YYYY/MM/YYYY-MM-DD`로 지정하여, 일기를 생성할 때마다 해당 연도와 월 폴더가 자동으로 생성되고 하위에 문서가 격리되도록 만들었다.

그리고 일기 템플릿 본문에서 오늘 진행한 프로젝트와 학습한 리소스를 위키링크로 자연스럽게 언급한다.

```markdown
## 오늘의 타임로그 & 작업

- 10:00 - 13:00 [[10 Projects/기업교육/삼O전자/Claude Code 교육|기업 맞춤형 AI 교육]] 1회차 진행
- 15:00 - 17:00 [[30 Resources/AI/Obsidian Second Brain with AI Agents|세컨드 브레인 아키텍처 정리]]
```

이렇게 작성하면, 나중에 특정 프로젝트 문서를 열었을 때 옵시디언의 백링크(Backlinks) 패널에 내가 8월 21일 일기에서 이 프로젝트를 언급한 내역이 자동으로 모여 보인다. 시간축(일기)과 주제축(프로젝트/리소스)이 인위적인 데이터 중복 없이 완벽하게 상호 참조되는 것이다.


## 실전 도메인 적용: 기업교육 관리 및 Dataview 실시간 자동 정산

세컨드 브레인이 단순한 메모장을 넘어 운영 도구로 작동하기 위해, 현재 진행 중인 실제 기업교육 일정 관리 및 급여 정산에 이 시스템을 실전 적용했다.

총 20여 건이 넘는 여러 기업교육 일정을 관리하기 위해 다음과 같은 계층 구조를 설계했다.

```text
📁 10 Projects/기업교육/
├── 📁 삼O전자/
│   ├── 📁 Claude Code 교육/
│   │   ├── 2026-08-26 삼O전자 Claude Code 교육.md
│   │   └── 2026-08-27 삼O전자 Claude Code 교육.md
│   └── 📁 비개발자 대상 Claude Code 교육/
└── 📁 기업교육_가이드.md (대시보드 MOC)
```

### Frontmatter 메타데이터와 Dataview 인라인 연산

일정 문서 상단에 시급과 유급시간 같은 원천 데이터(Source Data)만 Frontmatter에 정의해 둔다.

```markdown
---
type: project
title: "2026-08-26 삼O전자 Claude Code 교육"
client: "삼O전자"
course: "Claude Code 교육"
date: 2026-08-26
hourly_rate: 100000
paid_hours: 4
status: active
---
```

그리고 본문에는 옵시디언의 대표 플러그인인 Dataview 인라인 수식을 걸어두었다.

```markdown
- **적용 시급**: `= default(this.hourly_rate, 0)`원
- **유급시간**: `= default(this.paid_hours, 0)`시간
- **예상급여(세전)**: `= default(this.hourly_rate, 0) * default(this.paid_hours, 0)`원
- **예상 수령액(3.3% 원천징수 반영)**: `= round(default(this.hourly_rate, 0) * default(this.paid_hours, 0) * 0.967)`원
```

이렇게 구성해 두면, Frontmatter에서 유급시간이나 시급 숫자 하나만 바꾸어도 본문의 예상 급여와 3.3% 원천징수(소득세 3% + 지방소득세 0.3%)를 반영한 예상 수령액이 실시간으로 계산된다.

더 나아가 이 규칙을 `AGENTS.md`에 명시해 둠으로써, 내가 AI 에이전트에게 "다음 주 기업교육 일정 추가해줘"라고 명령만 하면 에이전트가 템플릿 양식에 맞춰 Frontmatter를 채우고, 폴더 계층에 문서를 생성하며, `기업교육_가이드.md` 종합 대시보드에 링크까지 자동으로 걸어준다.


## 크로스 플랫폼 모바일 동기화 (MacBook ↔ Android)

세컨드 브레인의 수집함(00 Inbox)이 제 역할을 하려면 이동 중에도 스마트폰으로 빠르게 메모를 던질 수 있어야 한다.

공식 유료 서비스인 Obsidian Sync를 쓸 수도 있지만, 개발자답게 무료 커뮤니티 플러그인인 `Remotely Save`와 Dropbox Basic (무료 2GB) 조합을 이용해 맥북과 안드로이드 기기간 크로스 플랫폼 동기화를 구축했다.

### 트러블슈팅: 볼트 네이밍 불일치로 인한 디렉토리 분기

동기화 설정 초기, 맥북에서 작성한 메모가 모바일에서 보이지 않는 문제가 발생했다. 원인을 분석해 보니 맥북의 로컬 볼트 디렉토리명(`Obsidian Vault`)과 모바일 앱에서 새로 만든 볼트 이름(`SecondBrain`)이 달라, 드롭박스 원격 루트 아래에 서로 다른 두 개의 하위 폴더로 데이터가 분기 저장되고 있었다.

- **원인**: `Remotely Save` 플러그인이 기본적으로 로컬 볼트 이름을 기준으로 드롭박스 경로를 잡는 동작 방식.
- **해결**: 모바일 앱의 볼트 이름을 맥북과 동일하게 통일하고, 드롭박스 원격 동기화 경로를 동일한 루트 폴더로 정확히 지정하여 양방향 자동 동기화를 정상화했다.

이제 스마트폰에서 이동 중에 떠오른 아이디어를 `00 Inbox`에 텍스트나 음성 메모로 던져두면, 맥북 앞에 앉았을 때 AI 에이전트가 이를 정제하고 분류할 준비를 마친다.


## 맺으며: AI는 사서(Librarian), 인간은 사유하는 사람

처음 이 프로젝트를 시작할 때의 내 기대감은 사실 아주 단순했다. "AI와의 대화창에서 나온 유용한 팁이나 코드 조각들을 대화창 밖으로 꺼내서 좀 덜 잃어버리고 싶다"는 소박한 마음이었다.

하지만 옵시디언의 로컬 마크다운 구조를 설계하고, 에이전트가 지켜야 할 운영 규칙(`AGENTS.md`)을 세우며, 블로그와 강의 정산 시스템까지 실제로 연동해 보면서 내 기대는 훨씬 더 큰 영역으로 확장되었다.

```text
[ 인간 (나) ]
  ├── 00 Inbox에 날것의 생각과 AI 대화 로그 투입
  ├── 핵심적인 의사결정 및 창의적 글쓰기 / 설계
  └── 매일의 일기(Daily Journal)와 회고 작성
        │
        ▼
[ AI 에이전트 (Antigravity / Claude Code) ]
  ├── AGENTS.md 규칙 기반으로 00 Inbox 문서 증류 (Distill)
  ├── 2단계 검색 기반으로 필요한 문서만 찾아 양방향 링크 연결
  └── 표준 템플릿 유지 및 메타데이터 자동 관리
        │
        ▼
[ Obsidian 볼트 ]
  └── 로컬 마크다운 기반의 투명하고 종속성 없는 Single Source of Truth
```

- **인간의 역할**: 폴더를 어디로 정할지, 링크를 어떻게 걸지 고민하느라 에너지를 낭비하지 않는다. 그저 `00 Inbox`에 날것의 생각과 대화 로그를 거침없이 던져두고, 핵심적인 판단과 사유에 온전히 집중한다.
- **AI의 역할**: `AGENTS.md`에 명시된 규칙에 따라 Inbox 문서를 요약·정제하고, 적절한 PARA 폴더에 배치하며, 지식 간 양방향 링크를 엮는 전담 사서(Librarian) 역할을 충실히 수행한다.

이번 구축을 통해 내가 확인한 것은 단순한 노트 정리의 효율화가 아니다. 인간의 뇌가 가진 창의적 사유 능력과 AI 에이전트가 가진 지치지 않는 구조화 능력이 가장 단순하고 투명한 파일 시스템 위에서 만났을 때 생겨나는 시너지였다.

앞으로 이 세컨드 브레인은 단순한 개인 노트에 머무르지 않을 것이다. 새로운 토이 프로젝트나 프로덕트를 개발할 때 내 개발 철학과 아키텍처 의사결정 히스토리를 AI 코딩 에이전트에게 즉각적으로 주입해 주는 Agent Context Store로 진화시키는 것은 물론, 나아가 생각의 흐름과 개발 작업 전체를 지탱하는 든든한 지식 파트너십으로 계속해서 확장해 나갈 것이다.
